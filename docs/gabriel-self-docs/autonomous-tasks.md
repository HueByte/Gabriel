# Autonomous tasks

## PURPOSE
How a delegated, long-running task works: the contract, the step loop you run inside, `task_checkpoint`, the reviewer, budgets, and when the user is pulled back in.

## USE WHEN
- A user message starts with `[Autonomous task - step N of at most M]` — you are inside a task right now.
- User asks how to delegate work, what a task contract is, or why a task paused, blocked, or failed.
- User asks what Gabriel can do unattended or how long it can work.

## QUICK REFERENCE

| Concept | Value |
| --- | --- |
| Entity | `AgentTask` (Core). Owns one conversation; the work happens in it. |
| Lifecycle | `draft → running ⇄ paused / blocked → completed \| failed \| cancelled` |
| Driver | `AgentTaskWorker` (hosted service) → `IAgentTaskRunner.RunStepAsync`, one step per task per pass, round-robin, one at a time |
| Step | One normal agent turn (`IAgentService.RunAsync`) with a generated step message; `Agent:MaxIterations` applies per step |
| End-of-step signal | `task_checkpoint(status: continue \| done \| blocked, progress, question?, summary?)` |
| Review | `ITaskStepReviewer` — separate tool-less call; JSON `{progress, done, feedback}` |
| Completion | Only when you checkpoint `done` **and** the reviewer confirms every done-criterion |
| Budgets | `AgentTasks:DefaultMaxSteps` (40), `DefaultMaxDurationMinutes` (180); resume adds `ResumeStepIncrement` (20) |
| Stuck guard | `MaxStepsWithoutProgress` (3) reviewer "no progress" verdicts in a row → blocked with a question |
| Error guard | `MaxConsecutiveErrors` (3) failed steps in a row → failed |
| API | `/api/tasks` — create, contract, approve, pause, resume, answer, cancel |

## DETAILS

### Contract
Creating a task drafts a contract from the user's goal with one LLM call (`ITaskContractDrafter`): **objective**, **done-criteria** (checkable conditions that together mean finished), **constraints**. The task stays a `draft` until the user reviews, edits, and approves it; approval requires at least one done-criterion. The contract is frozen once running and is repeated in every step message, so it survives compaction.

### What a step looks like from the inside
The user message of each step is generated by the runner: the step number and budget, the contract, optional **guidance** (the reviewer's feedback from the previous step, or the user's answer to your question), and the rules. Your job in one step:

1. Do one concrete piece of work toward the done-criteria. On step 1 with multi-part work, lay out a plan with `todo_write` first.
2. Deliver results as files — `write_project_file` / `edit_project_file` put them in the project's file area where the user can open them. Long chat replies are not deliverables.
3. End by calling `task_checkpoint` exactly once:
   - `continue` + `progress` — what this step achieved, concretely.
   - `done` + `progress` + `summary` — only when every done-criterion is met; `summary` is the user's final report (what was produced, where, what's left).
   - `blocked` + `question` — only when you truly cannot proceed without the user.
4. Then end your reply briefly. The next step arrives as a new user message.

### After each step
The runner reloads the task (the user may have paused or cancelled meanwhile), builds a transcript of the step, and asks the reviewer. Outcomes:

- `blocked` → task blocks with your question; no review.
- `done` + reviewer agrees → completed with your summary.
- `done` + reviewer disagrees (or the review was unreadable) → continue; the objection becomes the next step's guidance.
- otherwise → continue with the reviewer's feedback as guidance; a "no progress" verdict counts toward the stuck guard.

A step that ends without `task_checkpoint` is treated as `continue` and logged.

### User control
While running, the conversation belongs to the task: sends, edits, regenerates, and message deletes return `409`. Pause/cancel stop the in-flight step (same mechanism as the chat Stop button: partial text and every tool call are persisted consistently). A paused task resumes; a blocked one resumes when the user answers. Budget exhaustion pauses, and resuming grants a fresh budget.

### Background execution
The worker runs outside any HTTP request: each step gets its own DI scope with `CurrentUserOverride` set to the task owner, so preferences, memory scope, and project-file authorization are the owner's. Task state is persisted after every step, so a server restart resumes at the next step.

## INVARIANTS
- A task never completes on your claim alone — the reviewer must agree.
- Every step ends in a persisted state change (step logged, error recorded, paused, blocked, completed, failed); a broken step cannot spin.
- One running task drives a conversation; nobody else writes to it until it stops running.
- File writes are confined to the conversation's project storage; overwriting needs `overwrite: true`.

## PITFALLS
- Don't checkpoint `done` because you're out of ideas — the reviewer checks the criteria, and a disputed `done` just costs a step.
- Don't use `blocked` for questions you can answer with tools (search, read files, memory). Blocking stops all progress until the user returns.
- Repeating the same failed approach reads as "no progress" and trips the stuck guard; change approach instead.
- `task_checkpoint` outside a task returns an error — in a normal conversation, just answer.
